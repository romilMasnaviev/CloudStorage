# Что я понял после ревью проекта CloudStorage

## Архитектура и слои

- [x] Контроллер, сервис и инфраструктура должны знать разное.
- [x] Контроллер отвечает за HTTP-ответ, заголовки, Spring MVC и web-слой.
- [x] Сервис отвечает за бизнес-логику, а не за Spring-web детали.
- [x] Инфраструктурные детали MinIO не должны утекать в верхние слои.
- [x] Ошибки внешнего SDK нужно переводить в свои исключения как можно ближе к месту вызова.
- [x] Не всякая модель — это DTO или entity.
- [x] `Resource` — это внутренняя доменная модель файлового сервиса, а не `dto` и не `util`.
- [x] Логику путей лучше централизовать в одном месте, чем дублировать в нескольких слоях.
- [x] Иногда промежуточная внутренняя модель лучше, чем строковая “магия” в нескольких местах.
- [x] `Factory` создает внутреннюю модель, `Assembler` собирает DTO ответа.
- [x] Если объект нужен между сервисом и контроллером, это не обязательно DTO внешнего API.

## Path-логика и модель Resource

- [x] Path-логика не должна жить в DTO/response builder.
- [x] Внутренние MinIO-пути и пользовательские пути — не одно и то же.
- [x] Нужен единый источник правды для построения путей пользователя.
- [x] `ResourceFactory`/`ResourceBuilder` — нормальное место для создания `Resource`.
- [x] Лучше создавать `Resource` и маппить из него, чем дублировать path-логику в response-слое.
- [x] Корень пользователя и “папка пользователя как директория” — это разные форматы пути.
- [x] Нельзя случайно потерять `/` в конце directory path, иначе MinIO будет считать ключ другим.
- [x] `Resource` не должен лежать в `util`, потому что это не безликая утилита.

## DTO, response и внутренние объекты

- [x] `ResourceInfoResponse` — это внешний объект ответа.
- [x] Внутренний объект скачивания между сервисом и контроллером — это не обязательно `dto.response`.
- [x] Если объект содержит writer/stream-логику и используется внутри приложения, ему не место в `dto`.
- [x] Для скачивания файла/директории наружу обычно идет не JSON DTO, а бинарный HTTP-ответ.
- [x] Имя файла лучше отдавать через заголовки ответа, а не как JSON-поле рядом с бинарным телом.
- [x] `resourceType` может быть нужен серверу, но не обязан уходить клиенту в body.

## Потоки (`InputStream` / `OutputStream`)

- [x] `InputStream` — это источник байтов.
- [x] `OutputStream` — это приемник байтов.
- [x] `InputStream` — абстрактный класс, а не интерфейс.
- [x] `FileInputStream` — только один частный случай `InputStream`.
- [x] Поток MinIO — это тоже по сути `InputStream`, но не файл на диске.
- [x] Сервер при скачивании файла по сути делает `InputStream -> OutputStream`.
- [x] `transferTo()` нужен для копирования байтов из входного потока в выходной.
- [x] `transferTo()` не закрывает потоки.
- [x] Потоки закрывает `try-with-resources`, а не `transferTo()`.

## `ByteArrayOutputStream`, память и стриминг

- [x] `ByteArrayOutputStream` пишет данные в память.
- [x] Он не “отправляет данные клиенту”, а копит все байты в RAM.
- [x] Для маленьких данных это удобно.
- [x] Для больших файлов и архивов это опасно.
- [x] ZIP на сотни мегабайт через `ByteArrayOutputStream` может привести к OOM.
- [x] Для больших скачиваний лучше писать сразу в поток ответа, а не копить результат в памяти.

## ZIP и `ZipOutputStream`

- [x] `ZipOutputStream` — это `OutputStream`, который пишет ZIP-формат в другой `OutputStream`.
- [x] ZIP можно формировать на лету, не создавая его целиком в памяти.
- [x] `ZipEntry` — это описание файла внутри архива, а не содержимое файла.
- [x] После `putNextEntry()` все записываемые байты относятся к текущей entry.
- [x] После `closeEntry()` можно переходить к следующему файлу внутри архива.
- [x] Для нескольких файлов внутри ZIP не нужен отдельный `OutputStream` на каждый файл.
- [x] Нужен один `ZipOutputStream` на весь архив и несколько `ZipEntry`.
- [x] Если снизу у `ZipOutputStream` `ByteArrayOutputStream`, архив лежит в памяти.
- [x] Если снизу поток HTTP-ответа, архив сразу уходит клиенту.

## Скачивание файла и директории

- [x] Скачивание файла и скачивание директории можно привести к одной модели.
- [x] Для файла сервис может вернуть writer/лямбду, которая пишет файл в `OutputStream`.
- [x] Для директории сервис может вернуть writer/лямбду, которая собирает ZIP в `OutputStream`.
- [x] Для директории ZIP формируется из отдельных файлов, а не читается как один поток из MinIO.
- [x] Границы файлов внутри ZIP определяются не MinIO, а `ZipEntry`.
- [x] Для каждого файла директории нужно открывать свой `InputStream`.
- [x] Для каждого файла внутри ZIP нужен относительный путь entry, а не полный MinIO-ключ.
- [x] `InputStream` каждого файла внутри ZIP надо открывать и закрывать по одному внутри цикла.
- [x] `ZipOutputStream` должен жить на всю операцию скачивания директории.

## Spring MVC и `StreamingResponseBody`

- [x] `InputStreamResource` — это Spring-web обертка, а не доменная модель.
- [x] Сервису не стоит возвращать `InputStreamResource`.
- [x] `StreamingResponseBody` — это не готовое тело ответа, а инструкция, как писать в `OutputStream` ответа.
- [x] `StreamingResponseBody` выполняется позже, а не прямо в теле метода контроллера.
- [x] Лямбда для `StreamingResponseBody` — это отложенное действие.
- [x] `OutputStream` ответа приходит от Spring/Servlet infrastructure.
- [x] Сервис не должен знать про `StreamingResponseBody`, это web-слой.
- [x] Контроллер может адаптировать внутренний writer к `StreamingResponseBody`.

## Лямбды и функциональные интерфейсы

- [x] Лямбда — это короткая запись реализации интерфейса с одним методом.
- [x] По сути это объект с поведением, а не “магия”.
- [x] Лямбду можно понимать как анонимный класс в сокращенной форме.
- [x] `StreamingResponseBody` и свой writer можно связать через лямбду-адаптер.
- [x] Лямбда может захватывать внешние переменные.
- [x] Захватываемые переменные должны быть `final` или effectively final.
- [x] Это нужно потому, что лямбда может выполниться позже.
- [x] `Consumer<OutputStream>` по смыслу подходит, если нужно принять поток и что-то с ним сделать.
- [x] Но для I/O лучше свой интерфейс, если нужен `throws IOException`.
- [x] Свой writer-интерфейс должен описывать роль, а не реализацию.

## Исключения

- [x] Нельзя терять stack trace через `new RuntimeException(e.getMessage())`.
- [x] Лучше пробрасывать само исключение как `cause`.
- [x] Ошибки MinIO надо ловить ближе к MinIO-клиенту/репозиторию, а не в глобальном exception handler.
- [x] `NoSuchElementException` нельзя глобально маппить в `404`.
- [x] Доменные случаи “не найдено” должны иметь свои конкретные исключения.
- [x] Бизнес-ошибки и I/O-ошибки во время стриминга — это разные категории.
- [x] Ошибки до начала стриминга можно обрабатывать обычным `@ExceptionHandler`.
- [x] `IOException` во время стриминга — это уже особый случай, потому что ответ может быть частично отправлен.
- [x] Не стоит ловить слишком широкий `Exception`, если нужен только `IOException`.
- [x] Если операция по своей природе I/O, `IOException` — это естественное исключение, а не “стыдная” ошибка.

## Security, session и Redis

- [x] `SecurityContextHolder` и `HttpSession` — это не одно и то же.
- [x] `SecurityContextHolder` хранит контекст текущего запроса/потока.
- [x] `HttpSession` хранит security context между запросами.
- [x] Просто создать `SecurityContext` недостаточно — его надо положить в `SecurityContextHolder`, если нужен текущий запрос.
- [x] Сохранение контекста в session нужно для следующих запросов.
- [x] `Serializable` у `User` нужен не “просто так”, а из-за сериализации security context/session в Redis.
- [x] Spring Security сам по себе не требует сериализовать entity всегда, но в моем случае principal содержит `User`, а сессия уходит в Redis.

## Тесты и async

- [x] `StreamingResponseBody` в тестах требует учета async-обработки.
- [x] Нельзя сразу брать `MockHttpServletResponse`, если ответ стриминговый и async.
- [x] Для успешного стримингового ответа нужен `asyncDispatch`.
- [x] Ошибочные сценарии `400/404` могут не быть async, потому что падают до начала стриминга.
- [x] Для success и error у стримингового endpoint могут понадобиться разные тестовые helper-ы.
- [x] Разница между IDEA и Gradle может быть связана с таймингом async-ответа, а не только с логикой кода.
